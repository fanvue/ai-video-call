# Swap mode: self-hosted identity swap per clip over the Turbo pipeline

Status: service live on Modal for the POC (see `services/swap/README.md`); fal host written but blocked on serverless access for the Fanvue team. Client and server halves shipped: `swap` render backend, `generateClip` sends every rendered turbo clip through `server/swapClip.ts`, the swapped mp4 plays and its swapped last frame seeds the next clip, the studio overlay shows the per-clip swap report.

## Why

Director (fal minimax) and Lucy (Decart via fal) both enforce provider-side content policy on the live stream and cannot be configured otherwise. They are labelled SFW only in the setup screen. The clip backends (Turbo, Reference) already run with fal's documented `enable_safety_checker: false`, which fal permits for adult content between consenting adults. An identity-lock mode with the same content posture therefore has to run a model we host, with our own guards, not a third party's stream filter.

## What it is

The driving source is our own pre-rendered turbo clip, so there is no live frame stream: the server posts the finished clip to the swap service, which swaps the persona's face onto every frame (InsightFace `inswapper_128`), restores it (RestoreFormer++ via ONNX, replacing GPEN-BFR which turned out to also be Non-Commercial licensed) and re-encodes the clip at its native frame rate with the source audio. Output runs at the clip's 24/25 fps with no transport latency; the cost is a few seconds of GPU time per clip before it can play.

Every restored face crop is also pulled back toward the reference photo's own LAB color stats (`color_lock`, blend 0.5) before it's pasted back, so per-clip restoration bias can't compound into an increasingly warm/saturated look over a long session the way a raw restorer pass can.

Re-anchoring falls out of it: the swapped, restored last frame is the next clip's seed, so identity re-locks every clip instead of compounding. The service also reports the ArcFace cosine of the last frame against the reference before and after the swap, for a future gate that re-seeds from the original anchor when the underlying turbo identity has drifted too far.

The earlier per-frame JPEG-over-WebSocket transport (2 to 3 fps effective, 330 to 570 ms round trips) was replaced by this on 2026-09-22.

## Guards we keep (non-negotiable)

- Reference identity must be the synthetic persona photo from setup. No upload of a real person's face into this path; the existing `frameGuard` and reference vetting stay in front of it.
- 18+ only, one fictional adult. Existing frame checks run on the swapped clip, which is the one that plays.
- Service token never reaches the client. The server calls the service with a bearer token; the service fails closed when the token secret is missing.
- A swap failure is not a guard failure: the unswapped turbo clip plays and the overlay reports `failed` with the reason. No auto-retry.

## Service contract

- `POST /swapClip` with `Authorization: Bearer <SWAP_TOKEN>` and JSON `{ "video_url": "<mp4 url>", "reference_image": "<data uri>" }`.
- Response JSON: `video_base64` (h264 mp4, source audio copied), `last_frame_base64` (JPEG of the swapped last frame), `stats` (`frames`, `frames_with_face`, `fps`, `swap_ms`, `ms_per_frame`, `similarity_before`, `similarity_after`, `restored`).
- 403 without a valid token, 422 when the reference has no single face or the clip cannot be read, 500 on anything else.
- Detection, swap and restore on every frame, three frames in flight across threads, clips capped at 600 frames. A reference whose face fills the whole photo is retried with a replicated border, since the detector misses edge-to-edge faces.
- `POST /swapTail` with the same auth and body swaps only the last frame (last 0.3 s decoded, falling back to 1.5 s when the video track ends before the container). Response JSON: `last_frame_base64` and `stats` (`swap_ms`, `had_face`, `similarity_before`, `similarity_after`, `enhanced`, `enhance_ms`, `sharpness_before`, `sharpness_after`, `download_ms`). Measured 0.4 s of GPU, under 3 s wall from a laptop.
- `GET /health` is unauthenticated and doubles as the warm-up probe (`/api/live/swapWarm`, called by the client when a swap session starts).

## Server contract

- `renderBackendSchema` includes `"swap"`; `renderClip.ts` maps swap to the turbo backend like Lucy.
- `generateClip` with `LIVE_TUNABLES.SWAP_DEFER_CLIP` (default): render, then `swapTail` for chain clips (the swapped last frame is rehosted and becomes the next seed; on failure the raw last frame seeds and the fallback is logged), and the clip returns unswapped with `swap.status: "pending"`. The client's `swapRenderedClip` posts `{ videoUrl, referenceImageUrl, jobKind }` to `/api/live/swap` (authenticated, both URLs must be fal-hosted), which runs `swapClip` and fails open to the unswapped clip. With the tunable off the old inline path runs: render, then `swapClip` (fetch reference as a data URI, call the service, rehost the mp4 and last frame on fal storage), then frame checks and seed extraction on the swapped clip. GPU cost is `swap_ms` at `LIVE_TUNABLES.SWAP_COST_PER_SEC_USD`.
- `clipResultSchema.swap` carries the report to the client; `StudioOverlay` renders it on the last-clip line.
- Env: `SWAP_SERVICE_URL` (https base of the Modal app) and `SWAP_TOKEN`; either missing makes every swap clip report `failed`.
- Capacity: `max_containers=4`, `buffer_containers=2`, `scaledown_window=600`. A prod session showed `serviceMs` of 14 to 21 s against `swap_ms` of 6 s: the fourth concurrent clip queued behind a ~15 s cold start, the beat and bridge idles were late, and the player fell back to cuts. Two warm spares absorb that; the log line carries `downloadMs` so a slow fal fetch is told apart from queueing. The next session then measured a 93 s cold boot (image pull; the models load in 5 s) with the autoscaler never adding a second container, so the greeting swap hit its budget, the join took 54 s, the greeting ended on a 50 s hold and the first reply took 47 s. Now `min_containers=1` keeps one container warm around the clock (about one L40S hour of spend per idle hour, the lever to turn off when the spike is parked) and `@modal.concurrent(max_inputs=3)` lets that container take the join burst at once rather than one clip at a time. `SWAP_GREETING_BUDGET_MS` dropped to 20 s: past a warm swap the container is cold, and the reference-to-video greeting already carries the identity, so playing it unswapped is the faster join. Even warm, the container completes one clip every 6 to 7 s whatever `@modal.concurrent` allows (completions in prod were spaced exactly one execution apart), and fillers submitted while a reply rendered put 7 to 15 s of queue in front of its swap; the pipeline now holds new fillers while a request is in flight unless the shelf is bare (`fillIdleStockpile`).

## Open decisions

- Whether to chunk the swap (2 s segments, playback after the first). The per-clip delay is currently covered by two idles in flight and idle length tracking production time (see LIVE_ENGINE.md); chunking would let a single reply reach the screen sooner.
- No timed scene reset. Measured on a 5-generation chain (turbo idle hold, swap, last frame, repeat): the face stays locked (cosine 0.91 to 0.93 after every swap) but the framing zooms in generation by generation and the picture goes soft (Laplacian variance 108 on the upload, 14 after one generation, 9 to 11 after three to five). A 60 s cut back to the trusted frame was shipped against the softness and reverted: every reset read as a jump. The per-clip SeedVR2 restore below carries the softness; the zoom is an open item. 2026-09-22: re-ran a 5th-generation clip (`degrade-gen5.mp4`) through the new RestoreFormer++ + color-lock swap; ArcFace cosine still holds (0.91), but the frame still shows heavy eye-shadow-like contouring and reddish oversaturation ("clown makeup") the color-lock did not remove, since it corrects mean tone/contrast, not the compounding restorer-hallucinated feature exaggeration. Root cause is still open: most likely the full-clip restore pass (`RESTORE_BLEND`) running on every frame of every generation, each one diffusion-conditioned on the previous generation's already-restorer-biased face. Needs a live multi-generation A/B (fresh fal renders, not a pre-existing test file) to confirm before touching `RESTORE_BLEND` or gating full-clip restoration further.
- Seed restoration: the swap service runs FaceFusion's Real-ESRGAN x2 export over the swapped last frame and resizes it back to the clip size before returning it as the next seed (`enhance_frame`, 73 ms on the L40S; Laplacian sharpness 38 -> 161 on a 5th-generation frame, ArcFace cosine unchanged at 0.91). It is in the response, so every chain clip and bridge idle seeds from the restored frame with no extra round trip. It only runs on frames below `ENHANCE_MAX_SHARPNESS` (Laplacian 80): prod frames at 108 to 128 came out of it softer (98, 112), since the x2 model denoises texture it did not need to rebuild, while a 5th-generation frame at 38 still comes back at 78. The earlier fal SeedVR2 pass timed out at 15 s on every prod call and ran in the background, so the beat after a reply had already seeded from the raw tail; swap mode no longer calls it (`UPSCALE_INTERVAL_MS` stays for turbo and reference). Bake-off notes for the fal restorers, warm latency on the 5th-generation frame: NAFNet 1.8 s (no visible change), SeedVR2 2.1 s (real texture back), clarity 4.4 s (mild), photo-restoration 9 s (redesigned the face), Topaz Recover 3 85 to 117 s.
- Re-anchor gate threshold on `similarity_before`; measure a session first.
- Restorer blend (0.8) and whether to add a full-frame upscaler; both are second-order next to the face.
- Moving the Modal app to a Fanvue workspace; the inswapper research-only license (RestoreFormer++ replaced GPEN-BFR for the restorer's own Non-Commercial license, but the swapper itself, inswapper_128, is still research-only and unresolved).
